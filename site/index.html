2. MVC 패턴

MVC는 애플리케이션을 Model(데이터·비즈니스) / View(화면) / Controller(요청 제어)로 나누어 역할을 분리하는 설계 패턴입니다. 화면을 바꿔도 로직을 건드리지 않고, 로직을 바꿔도 화면을 건드리지 않게 하려는 것이 목적입니다.

역할 분담

  • Model — 상태·규칙. 화면을 모릅니다.
  • View — 모델을 보여주기만. 로직 금지.
  • Controller — 입력 해석 → 모델 호출 → 뷰 선택. 얇게 유지!

Spring MVC 는 “Model 2 + Front Controller”

  • 모든 요청이 DispatcherServlet 한 곳으로 들어옴 (Front Controller)
  • 공통 처리(인코딩, 예외, 인터셉터)를 한곳에서 처리
  • 컨트롤러는 서블릿을 직접 상속하지 않고 POJO + 어노테이션

응답 방식 갈림길 : 뷰 렌더링 vs JSON

요청 값 받는 3가지 (자주 나오는 비교)

어노테이션값의 위치예변환 주체
@PathVariableURL 경로/posts/1타입 변환
@RequestParam쿼리스트링 / 폼/posts?page=2타입 변환
@RequestBodyHTTP 본문(JSON){"title":"…"}HttpMessageConverter
@ModelAttribute폼 필드 → 객체title=a&content=b데이터 바인더

4. IoC · DI (제어의 역전 · 의존성 주입)

IoC (Inversion of Control)

객체 생성과 연결의 제어권이 개발자 코드에서 컨테이너로 넘어간 것. 우리는 “무엇이 필요한지”만 선언하고, 컨테이너가 만들고 관리합니다.

DI (Dependency Injection)

IoC 를 구현하는 방법. 필요한 의존 객체를 외부(컨테이너)에서 넣어주는 것 (생성자 / 세터 / 필드).

주입 방식 3가지 비교

빈이 여러 개일 때

빈 생명주기 (단계별로 눌러보기)

스코프

스코프의미비고
singleton컨테이너당 1개 (기본값)상태(필드)를 두면 동시성 문제 → 무상태로 설계
prototype요청할 때마다 새로 생성소멸은 컨테이너가 관리하지 않음 (@PreDestroy 호출 X)
request / sessionHTTP 요청 / 세션당 1개웹 환경 전용

5. AOP (관점 지향 프로그래밍)

로그·트랜잭션·보안·시간 측정처럼 여러 곳에 반복되는 횡단 관심사를 핵심 로직에서 분리해 한곳(Aspect)에서 관리합니다. Spring AOP 는 대상 객체를 프록시로 감싸 메서드 실행 시점에 부가 기능을 끼워 넣습니다.

용어 한 장 정리

호출 순서 시뮬레이터

대상 메서드 호출이 프록시 안에서 어떻게 진행되는지 단계별로 확인하세요.

순서 암기 들어갈 때: Around → Before → 대상 / 나올 때: AfterReturning(or Throwing) → After → Around(이후). 어드바이스가 여러 Aspect 에 있으면 @Order 숫자가 작을수록 바깥쪽입니다.

Aspect 코드

포인트컷 지시자의미예
execution메서드 시그니처 매칭 (가장 많이 사용)execution(* com..service.*.*(..))
within특정 타입/패키지 내부within(com.example.blog.service..*)
@annotation특정 어노테이션이 붙은 메서드@annotation(com.example.Timed)
bean빈 이름 매칭 (Spring 전용)bean(*Service)

프록시의 한계 : 자기 호출 (self-invocation) 단골 함정

  • 해결: 별도 빈으로 분리해서 주입받아 호출 (가장 권장) / 외부 진입 메서드에 어노테이션 적용
  • 같은 이유로 private · final 메서드, new 로 직접 만든 객체에는 적용 안 됨
JDK 동적 프록시CGLIB
방식인터페이스 구현 프록시대상 클래스를 상속한 프록시
조건인터페이스 필요final 클래스/메서드 불가
부트 기본proxyTargetClass=true → CGLIB 기본 (인터페이스가 있어도)

6. PSA (Portable Service Abstraction)

PSA = 이식 가능한 서비스 추상화. 특정 기술(JDBC, JPA, Redis, Tomcat …)에 종속되지 않도록 일관된 추상 인터페이스를 제공해, 코드를 바꾸지 않고 구현 기술만 교체할 수 있게 하는 설계입니다.

@Transactional 핵심 정리

속성설명
readOnly = true읽기 전용 힌트. 조회 메서드에 사용 (flush 생략 등 최적화)
rollbackFor기본은 RuntimeException · Error 만 롤백. 체크 예외는 rollbackFor = Exception.class 지정
propagation기본 REQUIRED(기존 트랜잭션 참여, 없으면 생성). REQUIRES_NEW(항상 새로 생성)
isolation격리 수준 (기본: DB 기본값)
동작 원리AOP 프록시가 메서드 앞뒤로 begin / commit / rollback → 자기 호출·private 메서드에는 적용 안 됨
AOP 와 PSA 의 관계 @Transactional 은 AOP(프록시로 가로채기) + PSA(PlatformTransactionManager 추상화) 가 함께 만든 기능입니다. 시험에서 “@Transactional 이 이용하는 두 기술”로 나옵니다.

암기 문장

  • 요청 흐름: DispatcherServlet → HandlerMapping → HandlerAdapter → Controller → … → ViewResolver/MessageConverter
  • 빈 생명주기: 생성 → 의존성 주입 → @PostConstruct → 사용 → @PreDestroy, AOP 프록시는 초기화 직후 BeanPostProcessor 에서 생성

  • 어드바이스 순서: Around → Before → 대상 → AfterReturning/Throwing → After → Around(후)
  • 컴포넌트 스캔: 메인 클래스 패키지 + 하위
